Guide 4 · Day 4 · Monday 28 September

Loops and graphs, in parallel

The Carrot Wall project · the 2-hour block, at your pace

This morning: what a graph is, how it levels up your loop, and how to run work in parallel without the agents, the ports or the bill getting away from you. This guide is the experiment. You make the wall safe for two worktrees, deliver two changes at the same time as two loops, then let a graph take one change and slice it into pieces that run in parallel. Along the way you write down where parallel work paid off and where it fought you. Then you fix one thing and push the branch. The log matters more than the feature.

Start hereBefore you start

  • Your fork is pushed from last week. Start a branch for today from it: git switch -c day4-parallel.
  • Claude Code is recent: claude --version. Sessions messaging each other needs v2.1.224 or later.
  • You have run claude once in the repo root and accepted the trust prompt. claude -w refuses to start in a folder you have not trusted.
  • Docker is running if you use Compose. The scripts also use lsof, which comes with macOS.
  • Optional, from this morning: /statusline show the worktree, context used and session cost, and /doctor once before you copy your setup into two worktrees.
What this block is for

This is an experiment, not a feature sprint. You run the same feature three ways and write down what happened. The log you leave with matters more than the code.

In class you automate to learn where it breaks. At work, the rule from this morning holds: let a graph drive, and scale it, only once you trust the process. Not while you are still learning it.

Step 1Make the wall safe for two worktrees

This morning's table of what breaks, fixed at the source. You can ask Claude to make these changes: start it at the repo root, in plan mode, paste this step, and check its plan against the list before you approve. That is rung 2 of this afternoon's ladder.

Keep worktrees out of git

Compose ports come from the environment

docker-compose.yml · the two ports lines
  api:
    ports:
      - "${API_PORT:-8010}:8080"

    ports:

Without a .env nothing changes: master still gets 8010 and 3010.

Tests pick a free port

# Tests take any free port, so two test runs never collide

Quarkus already reads QUARKUS_HTTP_PORT from the environment for dev mode, so the API itself needs no other change.

Playwright starts servers on this worktree's ports

apps/web/playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

const api = process.env.API_PORT ?? '8080';
const web = process.env.WEB_PORT ?? '4200';

export default defineConfig({
  testDir: './e2e',
  fullyParallel: true,
  reporter: 'list',
  use: { baseURL: `http://localhost:${web}` },
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
  webServer: [
    {
      command: `cd ../api && ./mvnw quarkus:dev -Dquarkus.http.port=${api} -Ddebug=false`,
      url: `http://localhost:${api}/api/wall`,
      reuseExistingServer: false,
      timeout: 120_000,
    },
    {
      command: `npm start -- --port ${web}`,
      url: `http://localhost:${web}`,
      reuseExistingServer: false,
      timeout: 60_000,
    },
  ],
});
Why reuse is off

With reuse on, a second e2e run finds a server already on 4200, uses it, and tests the other worktree's code. Everything passes, which is why nobody notices. Off means Playwright starts its own servers on this worktree's ports, or fails loudly if something is already there. Step 7 has a gentler version once your ports are per worktree.

Run the wall once from the main checkout, the way you always do, to check nothing broke: both apps start on 8080 and 4200, and cd apps/web && npx playwright test passes with nothing else running.

Step 2Three scripts, and two worktrees up at once

scripts/wt-up.sh · run once, inside a new worktree
#!/usr/bin/env bash
set -euo pipefail
slot=${1:?usage: scripts/wt-up.sh <slot 1-9>}
api=$((8080 + slot*10)); web=$((4200 + slot*10))
cat > .env <<EOF
COMPOSE_PROJECT_NAME=wall-$(basename "$PWD")
QUARKUS_HTTP_PORT=$api
API_PORT=$api
WEB_PORT=$web
DEBUG_PORT=$((5005 + slot))
EOF
(cd apps/web && npm ci --prefer-offline)
echo "api :$api  web :$web"
scripts/wt-down.sh · stop the slot and remove the worktree
#!/usr/bin/env bash
set -euo pipefail
set -a; [ -f .env ] && . ./.env; set +a
for p in ${API_PORT:-} ${WEB_PORT:-}; do
  pids=$(lsof -ti tcp:$p || true)
  if [ -n "$pids" ]; then kill $pids; fi
done
docker compose down -v --remove-orphans || true
wt=$PWD
cd "$(git rev-parse --git-common-dir)/.."
git worktree remove "$wt"
git worktree prune
scripts/dev.sh · run the api, the web app or the e2e suite on this worktree's ports
#!/usr/bin/env bash
set -euo pipefail
set -a; [ -f .env ] && . ./.env; set +a
case "${1:-}" in
  api) cd apps/api && exec ./mvnw quarkus:dev -Ddebug="${DEBUG_PORT:-5005}" ;;
  web) cd apps/web && exec npm start -- --port "${WEB_PORT:-4200}" ;;
  e2e) cd apps/web && exec npx playwright test ;;
  *)   echo "usage: scripts/dev.sh api|web|e2e" >&2; exit 2 ;;
esac
chmod +x scripts/*.sh
git add -A && git commit -m "Parallel-safe wall: ports per worktree, three scripts"

Every new worktree must start from this commit, not from master. By default Claude Code branches a new worktree from the default branch on the remote. Tell it to branch from where you are instead, in your personal settings in the main checkout:

.claude/settings.local.json
{
  "worktree": { "baseRef": "head" }
}

Try it with two throwaway worktrees

  1. Terminal 1, in the main checkout: claude -w try-1. In the session: /rename try-1, then ! scripts/wt-up.sh 1.
  2. Terminal 2: cd .claude/worktrees/try-1 && scripts/dev.sh api. Terminal 3, same folder: scripts/dev.sh web.
  3. Do the same with try-2 and slot 2.
  4. Open http://localhost:4210 and http://localhost:4220. Post on one: it must not appear on the other. Each worktree has its own database.
  5. Check who is listening: lsof -nP -iTCP -sTCP:LISTEN | grep -E ':(8090|8100|4210|4220|5006|5007)'.

Tear down in this order

  1. Stop the servers with Ctrl+C.
  2. Exit the Claude session. Because you named it, Claude asks whether to keep the worktree: choose Keep.
  3. From a terminal in the worktree folder: scripts/wt-down.sh.
Why the order matters

While a session runs, Claude Code can hold a lock on its worktree, so git worktree remove refuses. And an unnamed session with no changes removes its worktree on exit by itself, taking .env with it, while the slot's servers keep running. Naming the session gets you the keep-or-remove question.

Step 4Run two loops at once

Two sessions, two worktrees, two slots, two changes. Each runs your own loop from plan to pull request, and their work overlaps in time. That overlap is the point: while one waits for you, the other keeps going.

Change AChange B
Sessionclaude -w change-a, then /rename change-a and /color blueclaude -w change-b, then /rename change-b and /color green
Ports! scripts/wt-up.sh 1: API 8090, web 4210! scripts/wt-up.sh 2: API 8100, web 4220
ServersAnother terminal in the worktree: scripts/dev.sh api and scripts/dev.sh webThe same, in its own worktree
The loopYour loop for A: /plan, you sign, /execute until greenYour loop for B, the same way

Suggested setup for both: Sonnet as the main model and /advisor opus. If your /execute is heavy, try a /goal instead: the tests pass, no test file was changed, stop after 15 turns. Every time one of them waits for you, write it down.

When the first one lands

  1. Commit A in its worktree, then check the other session is reachable with /list-agents.
  2. Send the message:
in the change-a session
Let @change-b know change A is committed on worktree-change-a.
Rebase on it and run the tests before you ship.
  1. In B, the rebase is where overlapping files meet: git rebase worktree-change-a, fix what conflicts, and run the tests again.
  2. Run the end-to-end suite on B's slot: scripts/dev.sh e2e. Stop B's own servers first; Playwright starts them itself.
Why the rebase needs no push

Both worktrees share one .git, so A's branch is visible from B's folder the moment it is committed. There is nothing to push or fetch between them.

Ship, then log

Two pull requests. If B needed A, stack B on worktree-change-a; if your /ship works out the base from slice-NN names, pass it the base branch instead. Before you exit each session, copy /usage into the log with the start and end times, every time you had to step in, and every collision.

Step 5Now the graph: one change that slices itself

Two changes at once was the first kind of parallel: you split the work by ticket. Now the second kind. One change goes into a graph, and the graph splits it into slices that run at the same time inside it, each in its own worktree, each reviewed. Pick a Tier-3 change with an API side and a web side: 29, the upvote leaderboard, or 32, the presence counter.

First, the contract

  1. In the main checkout, on your branch, run your loop up to the plan: /intent, then /spec.
  2. Write the contract into the spec: the endpoint's path, the request, the response with one example, and the error cases. Add one @QuarkusTest that calls it and fails today.
  3. Commit. The contract is what lets the API slice and the web slice run at once without waiting for each other.

Then let the graph build it

the prompt
use a workflow to build #NN from docs/specs/NN-<slug>-plan.md.
First split it into slices that can run at the same time against the contract,
for example api and web. If it does not split cleanly, keep it as one slice.
Each slice gets one builder in its own worktree, on Sonnet. It implements the slice,
runs the unit tests only (./mvnw test in apps/api, npm test in apps/web) and returns
the files it changed and the test output.
Then one reviewer per slice, on Opus, with fresh eyes: try to fail it against the spec
and the contract, and return a verdict with evidence.
  1. When Claude asks to run it, choose View raw script first. Find the split, the worktrees, the models and the reviewers from this morning's slide.
  2. Watch it in /workflows: phases, agents, tokens.
  3. When it finishes and you like the shape, select the run and press s to save it as build-slices in .claude/workflows/.
  4. The builders' worktrees stay on disk with their changes: git worktree list. Keep what you want and remove the rest with git worktree remove.
Why unit tests only

A workflow's worktrees do not run your wt-up.sh. They have no slot ports and no node_modules until someone runs npm ci there. End-to-end tests belong in a slot you set up. That difference is one of the things to write down.

Log it as run 2: the tokens and time from /workflows, whether it split the change the way you would have, what the reviewers found, and how often you stepped in. A workflow takes no input once it starts, so the honest answer may be zero, and that is a finding too.

Step 6Read the log: where it worked, where it didn't

Ten minutes, with the log open. Answer in the file, one line each.

  • Did the two changes really overlap in time, or did one wait on the other most of the block?
  • Where did they collide? Was the rebase worth it, or should one simply have gone first?
  • Did the graph split the change the way you would have, and did the slices really run at once?
  • Which found more real problems in review: your loops or the graph's reviewers?
  • How far did each run move your /usage bars, per change, and was it worth it?
  • Every time you stepped in: could a gate, a rule or a script have done it for you?
  • Which kinds of tickets would you run this way again, and which would you keep as one loop, or plain plan mode?
Say it straight

"Parallel was slower here" is a good result. Most coding work splits less than it looks. The point is to know where your line is, on your code, with numbers.

Step 7Improve the experience: fix one thing

Pick the row that fought you most. Fix it in a file, not as a habit you have to remember. Then run the part it affected again, and write before and after in the log.

If this happenedTry this
Claude ran the servers or e2e on 8080 and 4200Claude's shell does not keep environment variables between commands, so it never saw your .env. Add to CLAUDE.md: In a worktree, start servers and e2e only with scripts/dev.sh. Or launch the session with CLAUDE_ENV_FILE pointing at a file of export lines: Claude sources it before every command.
e2e refused to start because your servers were upReuse only your own slot's servers: reuseExistingServer: Boolean(process.env.WEB_PORT). Safe once every worktree has its own ports.
/cleanup-worktree stopped master's serversIt kills whatever is on 8080 and 4200. Rewrite it to run scripts/wt-down.sh, which reads the slot's own ports.
A worktree didn't have your setup or the contractCommit before you create it, and check worktree.baseRef is "head".
Permission prompts in every session/fewer-permission-prompts in the main checkout. An approval you give in any worktree is saved in the main checkout's settings.local.json and applies to all of them.
You lost track of which window was which/rename, /color, and a status line showing the worktree and the cost.
The two changes collidedThey touched the same files. Pick pairs with less overlap, land one first and rebase the other, or run them one after the other: that is a result too.
The web slice sat waitingThe contract was too thin. Add examples and error cases, build the web side against a stub, or run the two as a stack instead of in parallel.
The reviewer agreed with everythingA different model from the builder, a "try to fail it" prompt, and a verdict that must cite evidence.
The workflow used more of your plan than it gave backA model per step, a smaller size guideline in /config, and one slice first.
Two Maven builds at once misbehavedBoth worktrees share ~/.m2. Run the builds one after the other, or give one slot its own with -Dmaven.repo.local, at the price of a full download.
Leftover worktrees, servers or containersgit worktree list and git worktree prune; docker compose -p wall-<name> down -v from anywhere.

VerifyProve it is clean

  • git worktree list shows only your main checkout, and nothing marked prunable.
  • lsof -nP -iTCP -sTCP:LISTEN | grep -E ':(8090|8100|4210|4220)' prints nothing.
  • docker ps shows no containers from your slots.
  • docs/parallel-log.md has three runs, the answers from Step 6, and one before and after.
  • Your fix lives in a file: CLAUDE.md, a script, a setting or a command.

HelpIf you get stuck

claude -w exits with a trust error: run claude once in the repo root and accept. Port is already allocated: another slot or a leftover, so find it with lsof -nP -iTCP:<port> -sTCP:LISTEN and docker ps. e2e is green but the feature is missing: check which ports it used; .env was not loaded or reuse is on. The frontend shows another worktree's posts: API_PORT in that worktree's .env points at the wrong slot. git worktree remove refuses: commit or stash what is in it, or run git worktree unlock <path> if it says locked. A worktree is marked prunable: its folder was deleted by hand; git worktree prune. The message never arrives: /list-agents in both sessions; check neither runs inside a container, and that crossSessionInbound is not set to hold or refuse. The workflow will not start: approve the prompt; on Pro, turn on Dynamic workflows in /config. Quarkus complains about the debug port: start it with scripts/dev.sh api, which gives each slot its own.

Your whole loop as three workflows

Understand, build, review and ship: three saved workflows, with your signature on the spec between the first and the second, and the merge after the third.

Let the graph pick the tier and drive

The whole loop from one command. The session holds the gates; the workflow you saved in Step 5 does the build. Point it at real tickets only once your five commands have stopped surprising you.

.claude/skills/ticket/SKILL.md
---
name: ticket
description: Take one ticket from triage to a pull request, stopping at each gate.
argument-hint: [issue number or URL]
disable-model-invocation: true
---
Ticket: $ARGUMENTS

1. Read the ticket. Ask the Day 2 questions in order, one line of reasoning each:
   - Could the diff be described in one sentence? Then Tier 1.
   - Does it cross modules, touch fragile code or carry security surface?
     Then Tier 3.
   - Will someone review it cold? Then Tier 3.
   - Otherwise Tier 2.
   When unsure, choose the higher tier. Propose the tier and stop.
   I confirm or override.
2. Tier 1: make the change here, run the checks, show me the output. Stop.
3. Tier 2: plan it in plan mode and stop for my yes.
   Then /execute until the checks pass. Stop.
4. Tier 3: run /intent and /spec. Show me five lines and the open questions, and stop.
   On my yes, run the build-slices workflow with the slices from the plan.
   When it returns, show each slice's verdict in five lines and stop.
5. Never merge and never skip a stop. When it is ready, tell me to type /ship.

Two details carry the design. Every stop shows five lines and the open questions, not the whole spec, so a signature stays a decision and not a click. And /ship keeps disable-model-invocation from Day 2, so the driver can take you right up to the pull request but cannot open it for you. When Claude Code asks to run build-slices, Yes, and don't ask again saves you that prompt next time.

A third slice in the background

claude --bg "implement the digest view for #29", then watch it in claude agents. Step in only when its row asks for you.
