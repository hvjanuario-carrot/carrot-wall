Step 1Finish the five, then try Opus 5.5

If a command is missing, Guide 2 Steps 2 to 6 have a starting body for each: five files, frontmatter pinned, one run each. Do not polish them yet. The run in Step 2 tells you what to fix.

Then the experiment from this morning. Opus 5.5 shipped yesterday, and Anthropic reports it at Fable level on most work for 40% less than Opus 5. Check that on your own work instead of trusting the table.

  1. Run /model and note which model the opus alias points to in your Claude Code today.
  2. Pick /spec or /plan and a feature from feature-ideas.md. Run it in a fresh session with the file as it is pinned now, and copy the output aside, for example to /tmp/spec-before.md.
  3. Change one line in the frontmatter, start a fresh session, and run the same command on the same input.
  4. Read the two side by side. Which one asked the question you would have asked? Which one invented something? Which one would you sign?
.claude/skills/spec/SKILL.md · the one line
---
name: spec
...
model: claude-opus-5-5      # was: opus
effort: xhigh
---

Keep whichever pin won, and put the reason in the commit message in one line. If you saw no difference, go back to the alias: opus follows the newest Opus on its own, while a full model ID stays exactly where you put it. Both are fine. The point is that you chose.

While you are in the file

The launch post on getting the most out of Opus 5.5 has three tips that apply to your five commands:

  • Delete "think carefully" and "think step by step". Opus 5.5 already thinks before every reply. Search your five files for those lines and remove them.
  • Name the finish line. Give the whole task in one message and say what done means, for example "the tests pass". Your /execute probably already does; check that /spec and /plan do too.
  • Put stopping rules in CLAUDE.md: when to carry on alone, and when to stop and ask you.

Step 2Give one step a door to the outside

Pick one path. Each one lets a step of your loop read something that lives outside the repo. When you are done, run /context again: the difference from your number is what the door costs, every turn. Write it in the commit message.

Path A · The ticket, through the CLI

Works on the wall today

GitHub issues are the ticket system the wall already has, and gh is already installed. Forks start with issues switched off: in your fork on GitHub, open Settings, then General, then Features, and tick Issues. Then point gh at your fork and open one issue, written the way a colleague would write it:

gh repo set-default <your-user>/carrot-wall
gh issue create --title "<a feature from feature-ideas.md>" \
  --body "<who wants it and why, in their words>"

Now give /intent the door: one line in the frontmatter, one paragraph at the top of the body.

.claude/skills/intent/SKILL.md · the changes
---
name: intent
...
allowed-tools: Bash(gh issue view *)
---
If $ARGUMENTS is an issue number, run `gh issue view $ARGUMENTS --comments`
first. Treat the issue as the originator's own words: quote them, do not
rewrite them. Anything the issue does not say goes under Open questions.
Never comment on the issue or change it.

(your existing body continues here)

allowed-tools pre-approves that one read while the command runs, so it does not stop to ask. It grants; it does not restrict. The limits live in Step 3. Run /intent <issue number> in a fresh session and check that the intent file quotes the issue.

Faster, once it works

A line such as !`gh issue list --limit 20` in the body runs before Claude reads the prompt, so the list arrives as text instead of a tool call. It is the same ! you added to /ship yesterday.

Path B · Jira, through MCP

If your team's Jira is Cloud

Atlassian ships a Rovo MCP server, and the official atlassian plugin bundles it:

/plugin install atlassian@claude-plugins-official
/mcp

Sign in from /mcp. Then find the exact tool names, in /mcp or by asking Claude to list the tools it has from Atlassian. Tools that come from a plugin are named mcp__plugin_atlassian_<server>__<tool>, and Steps 3 and 4 point at those exact names. Then add the same paragraph as Path A to /intent, reading a work item instead of an issue: "If $ARGUMENTS looks like a Jira key such as ABC-123, read that work item and its comments with the Atlassian tools first."

Read only, or a test project

Rovo MCP can create work items, move them and comment on them. Nothing in this step should write to a board your colleagues watch. If your Jira is Data Center, there is no Rovo MCP: take Path A today.

Path C · The browser, in /execute

The natural pick

Yesterday's /execute ends with evidence, and for the web app the best evidence is a real browser. Microsoft ships a Playwright CLI built for coding agents, lighter on context than their MCP server:

npm install -g @playwright/cli@latest
playwright-cli install --skills

The second line installs a skill into .claude/skills/ that teaches Claude the commands. Then add a verify paragraph to /execute:

.claude/skills/execute/SKILL.md · add to the frontmatter and the body
allowed-tools: Bash(playwright-cli *)

When the plan touches the web app: with the app running on
http://localhost:4200, use playwright-cli to open it, click through the
feature the way a user would, and take a screenshot. Then run the existing
end-to-end suite with `npm run e2e` in apps/web. Put what you saw, and what
the suite printed, in your evidence.

The wall already has two Playwright tests in apps/web/e2e/, and its config starts the servers for them. The suite checks what someone thought to test; the CLI is for the part nobody has written a test for yet: looking.

Prefer MCP? claude mcp add playwright -- npx @playwright/mcp@latest works too and costs more context. The tidy version gives the browser to one agent only; see Extra.

Step 3Decide what it may do on its own

Three lists in .claude/settings.json. allow runs without asking. ask stops for your yes. deny never runs. Claude Code checks deny first, then ask, then allow, and the first match wins. The file is committed, so the whole team gets the same rulebook.

Add a permissions block next to the hooks block that is already there. It stays one JSON object with one pair of outer braces.

.claude/settings.json · Path A
{
  "permissions": {
    "allow": ["Bash(gh issue view *)", "Bash(gh issue list *)"],
    "ask":   ["Bash(gh issue comment *)", "Bash(gh issue edit *)"],
    "deny":  ["Bash(gh issue close *)"]
  },
  "hooks": { ...what is already there, unchanged... }
}

For Path B, the same three lists with the tool names you copied: the read tools in allow, moving and commenting in ask, creating in deny. For Path C: Bash(playwright-cli *) and Bash(npm run e2e *) in allow.

Merging is not in any list on purpose. Step 4 guards it with a hook.

Test it: from a plain session, ask Claude to comment on your issue. You should get a prompt. Say no.

Step 4One hook that is not the formatter

Your fork already runs two hooks: the formatter after every edit, and the migration guard before every edit. Read both in settings.json first. They show the whole shape: read the tool call from stdin, decide, and to block, print a reason to stderr and exit with code 2. Claude reads the reason.

A permission prompt can be clicked through by someone tired at six in the evening. A hook cannot. So the hook gets the rule that must hold every time: Claude may open a pull request, and never merge one.

.claude/hooks/no-merge.sh
#!/usr/bin/env bash
# PreToolUse on Bash: Claude may open a PR, never merge one.
cmd=$(python3 -c 'import json,sys; print(json.load(sys.stdin).get("tool_input",{}).get("command",""))')
case "$cmd" in
  *"gh pr merge"*)
    echo "Merging is a human decision. Open the PR, show me the link, and stop." >&2
    exit 2 ;;
esac
exit 0
chmod +x .claude/hooks/no-merge.sh

Register it as a second entry in the PreToolUse array that already holds the migration guard. Do not add a second "PreToolUse" key.

.claude/settings.json · inside "hooks"
"PreToolUse": [
  { "matcher": "Edit|Write", "hooks": [ ...the migration guard, unchanged... ] },
  {
    "matcher": "Bash",
    "hooks": [
      { "type": "command", "command": "\"${CLAUDE_PROJECT_DIR}\"/.claude/hooks/no-merge.sh" }
    ]
  }
]

Test it twice: the script on its own, then through Claude.

echo '{"tool_input":{"command":"gh pr merge 3"}}' | .claude/hooks/no-merge.sh; echo "exit $?"
echo '{"tool_input":{"command":"gh pr view 3"}}'  | .claude/hooks/no-merge.sh; echo "exit $?"

The first prints the message and exit 2, the second exit 0. Then in Claude Code, /hooks shows it registered. Ask "merge the PR for this branch" and watch it bounce.

On Path B, the same shape guards the Atlassian write tools: match mcp__plugin_atlassian_.* and read tool_name from stdin instead of tool_input.command. Other rules worth a hook: yesterday's test-file guard (block edits to *.spec.ts and src/test/ during a fix), or the Stop hook from Guide 2's Extra.

A hook that does nothing is worse than none

The usual causes: the script is not executable, settings.json is no longer valid JSON (a missing comma), or an MCP matcher without .*, which matches nothing. The stdin test catches the first, /hooks the second. It happened to our own harness while we built the wall.

Step 5Read one plugin before you trust it

Pick one: security-guidance if you work on the backend, frontend-design if you work on the frontend, superpowers if you want to see a whole loop that someone else packaged. Read it in the order from this morning:

  1. /plugin, then Discover, then the plugin. Read Context cost and Will install. If it will not tell you, that is your answer.
  2. Every SKILL.md description. These are the triggers you are agreeing to. The source of each official plugin is on GitHub under anthropics/claude-plugins-official.
  3. hooks/hooks.json: what runs without asking, and on which events.
  4. .mcp.json: which systems it can reach, and which it can write to.
  5. Decide, and write one line in docs/plugins.md.
docs/plugins.md · one line each
security-guidance · install, project scope · hooks only (every edit, end of turn, commit), no MCP · the turn and commit reviews are extra model calls
superpowers · not now · its skills overlap our five commands and would compete with /spec

If you install it, prove it does something. For security-guidance, ask Claude to render a user's name with innerHTML in the web app and watch the warning come back. For a plugin with skills: a fresh session, a task that should match, and /context to check the skill loaded.

HelpIf you get stuck

Permission rules ignored: check the file is still valid JSON with python3 -m json.tool .claude/settings.json, and remember deny beats ask beats allow. Hook does nothing: /hooks, then the stdin test, then chmod +x. gh says "no default repository": gh repo set-default. Issues missing on your fork: they are off by default; see Path A. MCP server will not connect: /mcp shows the error, most often a missing sign-in. playwright-cli not found: open a new terminal after the global install. A skill never triggers: rewrite its description as the situations it is for, not the topic.

ExtraStretch, if you finished early

Give the browser to one agent only

A subagent can bring its own MCP servers. They connect when the agent starts and disconnect when it finishes, so the main session never pays for the browser's tools. Add to .claude/agents/test-runner.md:

.claude/agents/test-runner.md · frontmatter
mcpServers:
  - playwright:
      type: stdio
      command: npx
      args: ["-y", "@playwright/mcp@latest"]

Give the reviewer a memory

Add memory: project to .claude/agents/code-reviewer.md. After two reviews, read .claude/agent-memory/code-reviewer/MEMORY.md to see what it kept. Turning memory on also gives that agent Read, Write and Edit, so it can manage its notes; the wall's reviewer is told to report only, so check it still does.

Write the runbook

Take the incident-triage skill from this morning's slide and point it at what you can read on the wall: gh run list and gh run view --log-failed if your fork runs GitHub Actions, or your team's Sentry or Grafana if you have read access. Keep the last two lines: never restart, scale or delete; say what you would do next, and stop. Then ask "why did the last run fail?" without naming the skill, and check whether its description made it fire.

Run a security audit

/plugin install claude-security@claude-plugins-official, then /claude-security and scan only your branch's changes. It needs a paid plan and can use a lot of tokens, so scope it small. Patches land in a folder; applying one is your call.
