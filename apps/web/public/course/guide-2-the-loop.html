The Loop

The Carrot Wall project · the 2-hour block, at your pace

This morning you saw where the loop comes from and what each of its five steps must contain. This guide turns that into files: you write the two commands the wall does not have, make the three it ships yours, pin the model, effort, tools and invocation on each, push one real feature through your own loop, and then try to break it, because every place it bends is a line you add to a file. What you write here is what we refine together on Wednesday.

  • Yesterday's Step 4 you read the harness in .claude/. Today you rewrite the part of it that is the loop, and write the two pieces it does not have.
  • Open feature-ideas.md. You will pick one Tier-2 feature in Step 1 and push it through your own commands at the end.

Five commands you can defend, and one feature that went through them. Write, do not generate. The file is your interpretation of each step. Wednesday we refine them together; Wednesday evening you push the fork.

One sizing note first. On the tier slide, a Tier-2 feature folds intent and spec into the plan and signs off at plan and review. Today you run all five as files anyway, on purpose: you are testing five commands, and a command you never ran is a command you cannot defend. From tomorrow, size normally.

One format note, said once. Master's loop lives in .claude/commands/*.md, the older single-file form, which still works. You will write yours as .claude/skills/<name>/SKILL.md, the form the docs now prefer, because that is where the whole contract (model, effort, tools, invocation) is documented. Both run as /name. Moving the three existing ones keeps one owner per name, so /spec never has two definitions.

The contractWhat each step must contain, and what the file pins

The body of each file is the prompt you would type. The frontmatter is the part you kept forgetting. This table is the whole morning in one place; the steps below just fill it in.

Where the fields come from

All from the skills reference: description (name the situations, not the topic), argument-hint, model, effort, allowed-tools, disable-model-invocation, plus $ARGUMENTS in the body and !`command` to inject live output before the prompt runs. Effort levels are low · medium · high · xhigh · max; the default is high, and max is documented as prone to overthinking: do not pin it.

Step 1Pick a feature and write its intent by hand

Open feature-ideas.md and take a Tier-2 idea: one module, approach reasonably clear, real enough that every command below has work to do. Give it the next free number in docs/intents/ and a slug: 09-emoji-reactions, say, and write the intent yourself, using the wall's own 02-submit-a-post.md as the shape:

docs/intents/NN-slug.md · five headings, no solution
# Intent: [what is wanted, in plain words]

**Author:** you · **Date:** today · **Status:** draft

## Problem
## Proposed outcome
## Affected users and systems
## Constraints
## Open questions

By hand, this once, so you know what the command in Step 2 is supposed to produce. Ten minutes. If you cannot name an open question, you have not thought about it long enough.

Step 2Write /intent, the one the wall does not have

Its job is to get an intent out of your head and into the five headings, and to refuse to design. Create .claude/skills/intent/SKILL.md:

.claude/skills/intent/SKILL.md · a starting body: make it yours
---
name: intent
description: Capture the problem before any solution. Use when a ticket, idea or
  request arrives and nothing has been specified yet.
argument-hint: [the ticket, idea or problem in one or two sentences]
model: opus
effort: xhigh
---
Someone wants this: $ARGUMENTS

Interview me, one question at a time, until you can fill these five headings
honestly: Problem · Proposed outcome · Affected users and systems · Constraints ·
Open questions. Ask about who has the problem and how often, what done would
look like to them, and what must not change. Refuse to propose a design or name
files: if I drift into solutions, note the idea under Open questions and steer
back to the problem.

Then write docs/intents/NN-slug.md using the next free number, in the style of
the existing files there. List every open question you could not resolve; an
intent with none is a guess. No code.

Run it on a second idea from the backlog and compare its output with the intent you wrote by hand. Where yours is better, the difference goes into the file.

Step 3Make /spec yours

Move the shipped command into the skill form, then rewrite the body in your own words and add the contract:

mkdir -p .claude/skills/spec
git mv .claude/commands/spec.md .claude/skills/spec/SKILL.md
.claude/skills/spec/SKILL.md · the frontmatter to add, and the body to rewrite
---
name: spec
description: Turn an intent into a one-page spec with checkable acceptance criteria.
  Use after /intent, before any plan or code.
argument-hint: [path to the intent, or the feature in one sentence]
model: opus
effort: xhigh
---
Read $ARGUMENTS. Before writing any code, interview me one question at a time
about anything unclear: scope, edge cases, what done means, and which security
requirements apply: name them; do not leave security to be inferred.

When you have enough, write docs/specs/NN-slug.md (same number and slug as the
intent) with exactly: Problem · In scope / Out of scope · Acceptance criteria I
can check, each one a statement that is true or false · Constraints. One page.
No code.

The thing to defend on Wednesday is the acceptance criteria line. "Handles errors gracefully" is not checkable. "Posting with an empty message shows an error and stores nothing" is. Your body has to force the second kind.

Step 4Make /plan yours

mkdir -p .claude/skills/plan
git mv .claude/commands/plan.md .claude/skills/plan/SKILL.md
.claude/skills/plan/SKILL.md
---
name: plan
description: Turn an approved spec into a reviewable implementation plan.
  Use after /spec and before any code is written.
argument-hint: [path to the spec]
model: opus
effort: xhigh
---
Read $ARGUMENTS. Propose an implementation plan with: the files you will change
and why each one; the order of work; risks and open questions; and how we will
verify it works: which tests, which manual check. Do not write code.

Stop and wait for my review. When I approve, write the plan to
docs/specs/NN-slug-plan.md and stop again.

Run it inside plan mode: Shift+Tab until the status bar says so, or prefix the one prompt with /plan. If you want the model split from this morning, /model opusplan first. The mode is the enforcement: Claude can read and run read-only commands but cannot edit until you approve. The command is the shape: it decides what the plan must contain.

This is the first human gate of your Tier-2 loop. Read the plan with four checks: the files it names are the right ones, the order makes sense, the risks are real, the proof is concrete. Ctrl+G opens the plan in your editor so you can change it directly before anything runs. When Claude asks, pick approve and review each edit the first time through; you want to watch what your /execute does next.

Step 5Write /execute, the other one the wall does not have

This is the file I most want to read on Thursday, because it is where your team's definition of verified lives. Create .claude/skills/execute/SKILL.md:

.claude/skills/execute/SKILL.md · a starting body: the verification lines are yours to sharpen
---
name: execute
description: Implement an approved plan with verification after every change.
  Use only after a plan has been reviewed and approved.
argument-hint: [path to the approved plan]
model: sonnet
effort: high
---
Implement the plan in $ARGUMENTS, in the order it gives. After each meaningful
change run the checks that apply: ./mvnw test for the API, npm test for the web
app, and the build. For a bug, write the failing test first and make it pass.

If a test fails, fix the code, not the test: never weaken or delete an
assertion to get to green; if a test is wrong, stop and tell me why. When every
check passes, show me the evidence: the commands you ran and what they
returned, not a summary. Then stop; do not commit or push.

Notice the model. Execution is typing against a decided plan, so Sonnet at high is the right spend, and the command makes that choice for everyone who pulls the repo. Bring Opus back for a hard bug, not for the build. Underneath all of this, yesterday's migration guard and the two safety hooks keep running before every edit and every shell call, at no cost to speed. A command advises; they enforce.

Step 6Pin /ship

The shipped ship.md is the most worked file in the harness: it finds the predecessor slice, decides whether to stack on it or on master, refuses to open empty PRs. Read all of it before you move it. Then move it and pin the contract; the body mostly stays:

mkdir -p .claude/skills/ship
git mv .claude/commands/ship.md .claude/skills/ship/SKILL.md
.claude/skills/ship/SKILL.md · frontmatter
---
name: ship
description: Push the current branch and open a PR stacked on its predecessor slice.
argument-hint: [optional base branch]
disable-model-invocation: true
allowed-tools: Bash(git status *) Bash(git branch *) Bash(git push *) Bash(gh pr *) Bash(gh repo *)
---
Current state:
!`git branch --show-current`
!`git status --short`

(the shipped body continues below)

Two lines to be able to explain. disable-model-invocation: true means Claude can never decide to ship on its own: a command with side effects waits for a human to type the word. The allowed-tools list pre-approves exactly the git and gh calls the body needs, so shipping does not turn into ten permission prompts. And the !`…` lines run before the prompt is sent, so the command reads the real branch state instead of guessing.

Step 7Run the loop through your own commands

Now the feature from Step 1, end to end, using only what you wrote. Start a fresh session at the repo root for each stage: a plan on a clean window is a better plan.

  1. /spec docs/intents/NN-slug.md: answer honestly, push back when it assumes. Read the criteria as a reviewer would. Commit.
  2. Shift+Tab, then /plan docs/specs/NN-slug.md. The gate: four checks, edit directly, approve. Commit the plan file.
  3. /execute docs/specs/NN-slug-plan.md. Watch it. Esc the moment it drifts. Read the evidence it shows you, then run one check yourself and click through the feature in the browser against your own acceptance criteria.
  4. Before shipping, a second pair of eyes that is not yours and not the session that wrote the code: Use the code-reviewer agent to review the diff against docs/specs/NN-slug.md. Report gaps against the acceptance criteria, not style. The repo ships that agent; a reviewer in a fresh context is not biased toward code it just wrote. Fix what it finds that is real; ignore what is taste.
  5. /ship, or, if your permissions stop at a local commit, commit and push your branch by hand. Your GitHub, your call. The PR is the second human gate of a Tier-2 loop, and today the human is me.
The run is the test of the commands

Every place the run went wrong is a line in a file, not a note in your head. /spec let a vague criterion through? Tighten the body. /execute summarised instead of showing output? Sharpen the evidence line. Fix the file and run that stage again. That loop, run, notice, edit the command, is the whole afternoon and most of Wednesday.

Step 8Break it on purpose

You have a working loop. Now find out where it bends, because every bend is a line you add to a file. Pick two or three, ten minutes each, and edit the command after each one.

  • Starve /spec. Give it one vague sentence with no intent file. Does it interview you, or does it guess? If it guesses, the body needs to insist on the interview.
  • Run /plan at effort: low on the same spec, then at xhigh. Put the two plans side by side. That difference is what the effort pin buys, and it is the best argument you will have for it on Wednesday.
  • Hand /execute a plan with a wrong file in it. Does it follow the plan off a cliff, or stop and tell you? Decide which you want and write it down.
  • Ask for a shortcut. While a test is red, tell Claude to "just make the suite pass". Your body says fix the code, not the test. Does it hold? If it wobbles, that sentence needs to be sharper, and it goes on Wednesday's hook list.
  • Say "ship this" in words, without typing /ship. It must not be able to run the command itself. If it can, disable-model-invocation is missing.
  • Run a Tier-1 change straight, one prompt with the check in it, no commands. Notice which of the five steps you did in your head, and in what order. That is the sizing rule working.
What you are really doing

Every one of these is a test case for a command. You would not ship a function without one. The loop is the same: the run tells you which file to fix, you fix it, you run again. That is the job for the rest of the week.

Step 9One line, before you stop

Something surprised you today. A convention Claude missed, a command it needed, a wrong assumption it made twice. Put one line in CLAUDE.md before you stop. Claude can draft it; you decide whether it stays. That is how the file earns its place: one scar at a time, written by someone who was there.

VerifyProve the five are alive

  1. /context in a fresh session: five descriptions listed: intent, spec, plan, execute, ship. Not one duplicate /spec.
  2. Type / and check the argument hints read like instructions, not placeholders.
  3. /plan outside plan mode should still refuse to write code: the body says so. If it does not, the body is the bug.
  4. Ask Claude, in words, to "ship this" without typing /ship. It must not be able to run the command by itself.
  5. git status: the three old command files are gone, the five skill folders and your three docs are staged.
  6. At least one command changed because of a run. If all five still read exactly as you first wrote them, you did not push hard enough in Step 8.

HelpIf you get stuck

Post it on the wall at carrot.ecrop.dev or flag me down. Today's classic snags: a command that does not appear in /. Check the first line of the file is --- and the folder name matches; a plan that touches fifteen files for a small feature: your spec is too broad, shrink the scope; /execute weakening a test: that is the exact behaviour the body forbids, so make the sentence sharper and add it to Wednesday's list for a hook.
