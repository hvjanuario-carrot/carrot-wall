Part 2 · Step 1Run the wall, and keep it in view

Today's block is about seeing things change. Keep the wall running in a browser next to Claude Code the whole time: Angular reloads the page every time a file changes, so each change Claude makes shows up in seconds.

two terminals, at the repo root
cd apps/api && ./mvnw quarkus:dev
cd apps/web && npm start
  • Open localhost:4200 and put the browser beside your Claude Code window.
  • Look at the top of the wall: the question of the day, wall-prompt in apps/web/src/app/wall/wall.html, and the posts under it. That is what you redesign next.
  • Start Claude Code at the repo root on today's branch, signed in with your claude.ai account (/login).

Step 2Connect Claude Design to your code, and redesign the question

Start from the code, not from a blank canvas. Two ways; try the first one.

A · From Claude Code, with /design

in Claude Code, at the repo root
/design three different versions of the question of the day at the top of
the wall (wall-prompt in apps/web/src/app/wall/wall.html), using this
repository's styles and DESIGN.md. Keep the posts below it as they are.
  1. Claude drafts the versions as artboards on one canvas and opens it in your browser.
  2. Pick one. Click on it and change it directly: the text size, the spacing, a colour. Your edits save on their own.
  3. Back in Claude Code: "Implement the artboard I picked, including my edits, in wall.html and wall.scss."
  4. Watch localhost:4200 change as it writes the files.
What you need

/design is a research preview. It needs Claude Code 2.1.265 or later (claude --version) and a session signed in with /login, because the canvas is published as a private artifact on claude.ai. On your Team plan, artifacts are on by default.

B · From claude.ai/design

  1. Open claude.ai/design and create a design system with Import: connect GitHub and pick only DESIGN.md, apps/web/src/styles.scss and apps/web/src/app/wall/. Access goes through Anthropic's read-only Claude Design Import app.
  2. Add a screenshot of the running wall, and ask for the same redesign of the question.
  3. Export, then Send to local coding agent, and paste the prompt it gives you into Claude Code. If that prompt can't open the design, download the zip instead and point Claude at the README inside.
The Angular catch

Claude Design draws your look as HTML. It does not render real mat- components, and /design-sync only takes React design systems. So the last step always happens in Claude Code, which writes the Angular for you.

Step 4Build your code graph, then switch it on and off

in a terminal
npm i -g @colbymchenry/codegraph
codegraph telemetry off
codegraph install
cd carrot-wall
codegraph init
codegraph status

install adds codegraph to Claude Code; init builds the graph into .codegraph/, which stays out of git. Start a new Claude Code session and check /mcp shows codegraph as connected.

The comparison

  1. With codegraph on, ask: "How does a new post get from the form on the wall to the database, and what rate limits it?" When it answers, run /context and note the tokens used and how many tools it called.
  2. Open /mcp, select codegraph and switch it off. Run /clear.
  3. Ask exactly the same question. Run /context again.
  4. Switch it back on in /mcp when you're done.

Don't expect a big gap here

The wall is small, so searching is cheap and the difference may be modest. On a codebase ten or a hundred times bigger it grows. What you are learning is how to measure it, so you can decide on your own repositories.

To keep the graph fresh when you switch branch, add a git hook that runs codegraph sync:

.git/hooks/post-checkout, then chmod +x it
#!/bin/sh
# re-sync the code graph after every branch switch
codegraph sync >/dev/null 2>&1 &

Step 5Build a small knowledge graph of the wall

A code graph knows the code. A knowledge graph also takes in the documents: DESIGN.md, spec.md, feature-ideas.md, your intents and specs. Graphify builds one from a folder, and Claude Code can query it.

in a terminal
uv tool install graphifyy
graphify install
in Claude Code, at the repo root
/graphify .

It writes three files to graphify-out/: graph.html to open in a browser and click around, GRAPH_REPORT.md with the main concepts and connections, and graph.json, which is what Claude queries. Add graphify-out/ to .gitignore if it isn't there yet.

Ask it things

in Claude Code
/graphify query "which features in feature-ideas.md touch the rate limiter?"
/graphify path "WallComponent" "PostsResource"
/graphify explain "RateLimiter"
  • Compare an answer with what you get from a plain question, without the graph.
  • Open graph.html and look for a connection you didn't expect. The tags EXTRACTED, INFERRED and AMBIGUOUS tell you how sure it is about each link.
  • Ask yourself: would this be worth keeping up to date on your real product? That is the question from this morning.
Where your tokens go

Code is parsed on your machine with no model calls. The documents are read by the model, so building the graph uses part of your plan's usage. On the wall that is small.

Part 2 · ExtrasIf you finish early

A first knowledge base, kept alive

  1. Create kb/index.md with a header holding only okf_version: "0.2", and an empty kb/log.md.
  2. Ask Claude to draft three concepts from what you know about the wall, for example why posts are rate limited. Each gets type, title, description, sources, generated, status: draft and a stale_after as a full date and time.
  3. Read them, fix them, add yourself to verified as human:<your-name>, and set status: stable.
  4. Add the workflow below, so every merged pull request proposes an update for you to review.
.github/workflows/kb-update.yml
name: KB update on merge
on:
  pull_request:
    types:
      - closed
jobs:
  if_merged:
    if: github.event.pull_request.merged == true
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0
      - uses: anthropics/claude-code-action@v1
        env:
          GH_TOKEN: ${{ github.token }}
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            PR ${{ github.event.pull_request.number }} was merged.
            Read its diff. If it changes something kb/ describes, update those
            concepts, cite the PR in sources, set status: draft on anything new,
            add a line to kb/log.md, and open a pull request. If nothing in kb/
            is affected, do nothing.
          claude_args: |
            --allowedTools "Read,Write,Edit,Bash(git:*),Bash(gh:*)"
Three things to know

Test it on your fork first: on a fork, turn Actions on in the Actions tab. The workflow needs an API key in the repository's secrets; on a shared repository use an organisation key, not a personal login. And a merged pull request is untrusted input like any other: the prompt only lets it touch kb/ through a pull request you review.

A reuse step in your plan

You raised it this week: the agent writes code again that already exists. Add this section to your /plan skill, so the check happens before any code is written and you see it at the gate.

.claude/skills/plan/SKILL.md · add before the steps
## Existing code considered
Before proposing new code, search for code that already solves part of this:
the shared Angular components and services, the common Java module, the
FastAPI utilities. Use the code graph (codegraph), not only grep.
List what you found, one line each, and say for each: reuse it, extend it,
or why not. Only propose a new shared abstraction when the same logic exists
in three places or more. Otherwise keep it local.

After the change, /code-review reports reuse and simplification findings on your diff, and /simplify applies cleanups. In CI, SonarQube's quality gate already has a condition on duplicated lines in new code.

One rule

Connectors that send, like Outlook and Teams, ask before each action by default. Keep it that way. An email, a ticket or a comment can carry instructions meant for the agent.

Part 4The one lesson

If you keep one thing from the five days, keep this loop. Run it on your own work, not on the tool.

  1. Look at what you do. Where could this be faster if AI did it? The repetitive part, the part that doesn't need you.
  2. If it is faster, check the quality. How do you know the result is still right? A test, a review, a gate, a person.
  3. Then look again. Next week, next project, next tool. The answer changes, so the question never ends.
Why it matters

We are all in our own loop of getting better. The day we stop looking, we stop growing. The AI can do more and more of the work. What stays ours is the thinking: noticing the problem, fixing it, making things better. That is the part worth protecting.

Before you leave, write three lines at the bottom of your log, just for you: one thing you would hand to AI next week, how you would check it, and when you will look again.
